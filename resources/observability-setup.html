Observability Setup

FrontDesk AI · and the lab cluster it runs on
Grafana · Prometheus · Loki · Tempo — what is deployed, and how the pieces reach each other

The one-sentence idea. A running system is a black box. Observability is the practice of making it tell you three things about itself — numbers over time, lines of text about single events, and a map of one request as it moves through the parts. Grafana is the single window you look at all three through.

Everything on this page was checked against the running cluster rather than copied from a plan. Where something is configured but not yet working, it says so rather than pretending.

1 · The four tools, in plain words

Every one of these is a Grafana Labs project, and they are built to be used together. The easiest way to remember which is which is to think of a hospital.

Status — all four are deployed and carrying real data. Grafana, Prometheus, Tempo and, since 11 September 2026, Loki and its log shipper Promtail are all running in the monitoring namespace, and Grafana has a datasource for each. Logs from every one of the 31 sandboxes and from every deployed app are landing in Loki now, and the log ↔ trace jump works in both directions — all verified by querying the live cluster, not by reading the configuration.

2 · The big picture — one chat message, three signals

A participant asks FrontDesk AI a question. That single HTTP request produces all three kinds of evidence at once, each taking a different road to a different store.

3 · What FrontDesk AI reports about itself

The app does not get observed by magic. Roughly 300 lines in app/observability.py set up three exporters at startup, and every agent call is wrapped in one context manager, trace_llm_call("agent_name"), which starts a span, times it, counts its tokens and writes a correlated log line — all at once.

Metrics — seven numbers, served at GET /metrics

MetricTypeLabelsWhat it answers
frontdeskai_request_duration_secondsHistogramcategoryHow long a whole question took, end to end

frontdeskai_llm_tokens_totalCounteragentHow many tokens each agent burned — the cost driver

The agent label carries more than a name. A worker that reasons in a loop reports hr_react_iter_0, hr_react_iter_1 … and finally hr_worker_final. So the metric does not just say which agent ran — it draws the shape of how it thought. A series tagged _react_iter_2 means that worker used the very last reasoning step it was allowed.

Traces — one request, drawn as a tree

Each participant's app sets OTEL_SERVICE_NAME=frontdeskai-<their namespace>, so in Grafana's Explore screen they pick their own name out of the service dropdown and see only their own traces.

Logs — shipped, parsed, and searchable

Every log line the app writes is JSON, and Promtail does more than forward it. Its pipeline parses each line and promotes three fields — level, logger and agent — into Loki labels, which is what makes them fast to filter on. Everything else, including trace_id, stays inside the line.

That gives you queries like these, in Grafana’s Explore screen with the Loki datasource selected. The first is the one you will use most:

QueryWhat it gives you
{namespace="agenticaiu7"}Everything from one participant’s space
{app="frontdeskai", level="ERROR"}Only what went wrong, across the whole cohort
{app="frontdeskai", agent="hr_worker_final"}Only the lines one agent wrote
{app="frontdeskai"} |= "f36d8813"Every line belonging to one request, by its trace id
{app="frontdeskai"} | json | duration_ms > 5000Only the slow calls — the JSON is parsed at query time

The payoff: a log line and its trace are two views of one thing

Because the app writes trace_id into every line, and Tempo stores the same id on every span, the two stores can be joined — and Grafana is configured to do it both ways. From a log line, a regular expression finds the id and renders a View trace button. From a span, Grafana runs a Loki query that searches for the same id.

4 · The cluster side — and the one twist you must know

The same Prometheus that scrapes the app also watches the cluster itself: nodes, pods, the GPU, the LLM gateway. But on this cluster Prometheus is run in a special mode, and everything else follows from it.

5 · The dashboards — four questions, four screens

A dashboard is not a pile of graphs; it is one question, answered. These four are generated by Python scripts kept beside their JSON in this resources/ folder — the JSON is never hand-edited, because a hand-edit is a change nobody can review.

What the dashboards actually told us, running the real app. One user question fans out into 4.25 LLM calls and about 4,400 tokens. The slowest step and the dearest step are different steps — the supervisor eats 22% of the wall clock, while one worker's reasoning loop eats 54% of the tokens. And the average request takes 12.8s while the 95th-percentile request takes 26.2s. That gap is the whole argument for percentiles: one number is an anecdote.

6 · Why observability breaks silently — and how to tell

The single most useful thing to understand here. Both namespaces on this cluster deny all outbound network traffic by default, and you must open holes deliberately. Get it wrong and the symptoms are completely different depending on which signal you broke — and one of the three cannot break this way at all.

A short list of traps that have actually bitten, in this exact setup.
  • A ${…} in a Grafana provisioning file gets eaten. Fixed 11 Sep 2026, and the shape of it is worth remembering. The Loki datasource said url: ${__value.raw} — but Grafana treats ${…} in a provisioning file as an environment variable and substitutes it before the datasource is ever created, so the stored link target was an empty string and the View trace button went nowhere. Nothing errored; the datasource looked perfectly healthy. Caught by comparing the file inside the Grafana pod against what the API reported back — they disagreed. The fix is to escape the dollar: $${__value.raw}. Any Grafana link template that carries a $ needs the same treatment.
  • A dashboard renders empty. It is almost certainly pointed at the agent-mode Prometheus instead of prometheus-nuc. Agent mode replies “unavailable with Prometheus Agent” to every query.
  • A counter shows “No data” on a healthy app. Counters are only published after they first increment. A panel reading one needs or vector(0), otherwise a working app with zero escalations looks broken.
  • A percentile returns a suspiciously round number. Latency was once recorded in seconds into buckets sized for milliseconds, so every measurement fell in one bucket and p50, p95 and p99 all returned the same invented value. Fixed — but a pod on an older image still shows it, and a time range spanning the fix mixes two bucket sets and returns 10000, which is a bucket edge and not a latency.
  • A network policy you just applied seems not to work. Give it a few seconds. The first connection after applying one was refused and the identical call seconds later succeeded.
  • Someone runs helm upgrade prometheus. The scrape configuration on this cluster is hand-applied, not Helm-rendered, so an upgrade silently reverts it and takes every dashboard with it. Re-apply the saved copy afterwards.

If you remember only three things. One: metrics, logs and traces are three different questions — all three are now collected, and Grafana is the one window onto all of them. Two: on this cluster Prometheus collects but the NUC answers, so a dashboard aimed at the wrong one is silently empty. Three: a push that is blocked fails quietly, so an empty trace view is a network problem until proven otherwise — while logs, which are read off the node’s disk, cannot fail that way at all.
