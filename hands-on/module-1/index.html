Module 1 — Agents vs. Multi-Agent Systems

Day 1 hands-on · five labs, intermediate to advanced
One case file throughout · self-checked · solutions provided

How these labs work. Fill every BLANK, then run the Self-check cell under each section. It prints [PASS], [FAIL] or [TODO], and the last cell prints a Self-check tally.

You write real LangChain and LangGraph code in every lab. The Self-check cells assert on the objects you build — a bound tool, a compiled graph, a validated schema — so they are deterministic and do not need the model. Cells marked Run it for real put your code in front of the sandbox model; that is the part worth watching. Run All is always safe on an untouched notebook, and the score line is feedback, not a grade.

One case runs through all five: payment exceptions on a small synthetic ledger. Each lab carries forward what the previous one built, so work them in order.

Lab 1.1 — From a Stateless Call to an Agent Loop

What turns a model call into an agent — built by hand, then handed to create_agent.

  • Carry state the way LangChain does it — as a list of message objects you resend
  • Let the model choose a tool for real, with `bind_tools` and `tool_calls`
  • Close the loop by feeding results back as `ToolMessage`, and make it stop
  • Then replace the whole thing with `create_agent` + a checkpointer, and compare

Lab 1.2 — The Four Building Blocks

Each of the four blocks as a real LangChain object, then all four assembled over the case file.

  • Write tools with a real argument schema, and docstrings the model actually reads
  • Bound memory with `trim_messages` — including the token counter that breaks on this model
  • Turn a goal into a dependency-ordered plan with `with_structured_output` and Pydantic
  • Assemble all four blocks into one agent over the case file

Lab 1.3 — create_agent, and What a Tool Description Is Worth

The same agent twice, with opaque and with good tool descriptions. Measure the difference.

  • Build the same agent twice — once with opaque tool descriptions, once with good ones
  • Measure the difference in tool-selection accuracy against the live model
  • Make the agent return a typed Verdict with response_format, not prose
  • Read the message trace `create_agent` produces, and find where a run went wrong
1 blanks · 15 checks · solution: solutions/lab-1-03-create-agent-on-ramp.ipynb
50 minAdvanced

Lab 1.4 — One Agent or Three: Building the Same App Twice

One agent or three? Build both, find out which you would ship, then investigate the gap.

  • Build the same capability twice: one agent with three tools, three agents with one each
  • Run one eval set through both and find out which one you would actually ship
  • Find the bug the second architecture introduces — a handoff that loses information
  • Fix it with typed handoffs (response_format) and watch the accuracy come back
4 blanks · 25 checks · solution: solutions/lab-1-04-coordination-tax.ipynb
45 minAdvanced

Lab 1.5 — Challenge — The Decision Rubric, Made Executable

The rubric that answers “do we need multiple agents?” before anyone starts building.

  • Encode the “do I need multiple agents?” rubric as code that terminates early
  • Write the acceptance bar down before you look at any result
  • Feed Lab 1.4's real pass rates in and let them overrule the architecture you wanted
  • Have an agent produce the design-review record as a typed object, not a paragraph
