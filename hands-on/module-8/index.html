Module 8 — Safety & Guardrails

Day 3 hands-on · one lab, advanced
Ends in a real pull request · self-checked · solution provided

How this lab works. Sections 1 to 3 are ordinary lab work: fill every BLANK, then run the Self-check cell under each section. It prints [PASS], [FAIL] or [TODO], and the last cell prints your Score. Those checks are pure functions over a small in-memory store, so they are deterministic and need no model and no network. One cell marked Run it for real calls the sandbox model to show the attack landing; it prints rather than asserts, because model behaviour is not a thing to grade.

Section 4 is different, and it is the point of the lab. It acts on a real public repository — it creates a fork, an issue or a comment on one, a branch and a pull request, all under your own GitHub account and your own name. Nothing in it is scored, and every cell self-skips until you enter a token. You will need a classic personal access token with the single public_repo scope: GitHub does not let a fine-grained token write to a public repository you do not own.

Lab 8.1 — Poison the Example Store, Then Fix It

The thumbs-up button is an injection channel: one employee's text, retrieved into every other employee's prompt. Prove it, fix it, then send the fix upstream.

  • Reproduce a stored cross-user injection with the app's own few-shot code
  • Decide whether the missing check belongs at write time or at read time, and write it
  • Measure whether the model obeys the planted rule — and what makes it stop
  • Fork the app, raise the issue upstream, or comment if it is already raised
  • Open a pull request from your own account, with a regression test under it
