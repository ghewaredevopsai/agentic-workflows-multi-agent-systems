Module 7 — Multi-Agent System Evaluation

Day 3 hands-on · five labs, intermediate to advanced
One case file throughout · self-checked · solutions provided

How these labs work. Fill every BLANK, then run the Self-check cell under each section. It prints [PASS], [FAIL] or [TODO], and the last cell prints your Score.

Self-checks assert on objects, not on scores. You build the real thing — a create_agent under test, a typed Verdict, a BaseCallbackHandler that traces a run — and the checks run against those objects and against runs recorded in the notebook. That is deterministic and needs no endpoint. Cells marked Run it for real do call the sandbox model; they are never scored, because scoring a single live run is the mistake Lab 7.1 exists to teach.

Every blank asks a decision. The mechanics are given. What is left blank is the thing only understanding answers: which field a score can honestly be built on, which failure is disqualifying rather than merely low-scoring, which of two numbers goes in front of the person who owns the budget.

Nothing depends on a tracing backend. No graded cell touches Langfuse. The Langfuse cells print the field mapping and return when it is not configured, so an outage costs the demo and never a score.

Lab 7.1 — Non-Determinism, Measured

On ten cases, even a 35-point improvement cannot be established. Find out why, and what fixes it.

  • Build the agent under test — create_agent with a typed Verdict
  • Choose the one field of that verdict a score can honestly be built on
  • Decide what a run with no typed answer at all counts as
  • Watch the same system score differently run after run, and compute the range
  • Pick the rule that decides whether a difference between two versions is real

Lab 7.2 — Build the Tracer

Sixty lines, and it is a real BaseCallbackHandler. Afterwards a tracing product is a UI over something you understand.

  • Spans with parent links — the one link that makes a tree instead of a log
  • Separate a span's own time from its children's
  • Wire the store to LangChain and trace an actual agent run
  • Rank by time and by tokens, and find they name different villains
  • Decide which spans a tracing product must be told are model calls

Lab 7.3 — Outcome and Trajectory Assertions

Five recorded runs, as real message lists. Four pass every outcome check. One of them tried to release a sanctioned payment.

  • Write the outcome assertions everybody writes, over real recorded runs
  • Decide which tools an agent must never even attempt
  • Derive a step budget from signed-off runs instead of picking one by feel
  • Separate a low score from a disqualification — they do not trade off
  • Add a typed LLM judge for what an assertion cannot express
3 blanks · 26 checks · solution: solutions/lab-7-03-outcome-and-trajectory.ipynb
40 minAdvanced

Lab 7.4 — Locating the Failure

Eight failed runs. Without a trace all eight are “the agent hallucinated”. Seven of them are not.

  • Order the attribution ladder — the order is the design
  • Handle the run with three things wrong — the first one is the cause
  • Count the spend wasted downstream of each failure
  • Choose between the step that fails most often and the step that costs most
  • Break a tool on purpose and diagnose the run off your own trace
3 blanks · 20 checks · solution: solutions/lab-7-04-locating-the-failure.ipynb
45 minAdvanced · challenge

Lab 7.5 — Challenge: The Release Gate

Four candidates, a bar agreed in advance, and the best-looking version of all disqualified by one run out of fifty.

  • Write the acceptance bar down as a typed object, before you look at a result
  • Choose the gate's quality test — and find what the other one lets through
  • Decide whether a disqualifying behaviour is a reason or the end of the discussion
  • Put one number, in the right units, in front of the person who owns the budget
  • Produce a ship / do-not-ship decision with reasons for four real candidates
