Day 1 — The Agent Loop: Reasoning, Memory & State
Day 1 · Practical

Setup & the sandbox

4 questions
QWhich model are we using, and why not GPT-4 or Claude?▼
Quick answerThe sandbox serves one open-weights model through an OpenAI-compatible gateway, and it is already wired into your notebook. Nothing to install, no key to register.

Every notebook reads three environment variables that are injected into your sandbox, so ChatOpenAI(...) and create_agent(...) simply work. No lab hardcodes an endpoint — that is deliberate, so the same notebooks run anywhere.

Why not a frontier model? Because the point of Day 1 is architecture, not model quality. Every result you measure today — the tool-description gap, the coordination tax, the parser drift — is a property of how you built the thing, and it reproduces on any competent model. A stronger model would paper over some of them, which is exactly what you do not want while you are learning to see them.

One thing to know: the opencode CLI in your terminal does not use the same gateway. It runs on its own free models. So terminal behaviour and notebook behaviour are not comparable.

QA cell printed export LAB_LLM_BASE_URL=… instead of running. What happened?▼
Quick answerYour model settings were not visible to that kernel. The cell told you exactly which two variables to set rather than failing with a stack trace.

Every live cell in every lab is guarded. If the endpoint is not configured it prints the export lines it needs and carries on, so Run All never dies halfway. Open a terminal in the sandbox, run env | grep -i llm, and set what is missing.

Good news: most self-check cells do not need the model at all — they assert on the objects you built (a bound tool, a compiled graph, a validated schema). You can fill in every blank and pass every check while your access is being sorted out. You will only miss the Run it for real cells, which are the interesting half.

QWhy is the model sometimes very slow, and why do the labs turn “thinking” off?▼
Quick answerThe served model reasons before it answers, and that reasoning is billed as output tokens. Measured on this sandbox: 24.1s and 980 tokens with thinking on, 0.7s and 29 tokens with it off — for the same one-line answer.

The labs pass a vendor-specific flag through extra_body to turn it off, because you make a lot of calls today and a 34× latency difference would eat the session. The standard reasoning_effort parameter is ignored by this backend, which is a useful thing to know about self-hosted models generally.

It is a trade, not a free win. On the capstone's own eval set, turning thinking off took accuracy down until the prompts were rewritten as an explicit ordered procedure. That is why several labs give the model a numbered procedure rather than a vague instruction.

QCan I run these labs after the course, on my own machine?▼
Quick answerYes. Point the three environment variables at any OpenAI-compatible endpoint — a hosted provider, a gateway, or Ollama with its OpenAI shim.

The labs and solutions are generated from a single source and verified two ways: every solution must score full marks, and every untouched lab must survive Run All without an uncaught exception. Both checks run offline.

Package set: langchain 1.x, langchain-openai, langgraph 1.x and pydantic 2.x. The labs are written against LangChain 1.x specifically — see the create_agent question below for why that matters.

Day 1 · Module 1

Agents vs. Multi-Agent Systems

9 questions
QWhat actually makes something an “agent” rather than a chatbot with tools bolted on?▼
Quick answerOne thing: the model's output decides what happens next. If your code decides the order of steps, it is a workflow with an LLM in it — often the better build, but not an agent.

The useful test is the flowchart test: if you can draw the flow and it does not change with the input, you do not need an agent. Control flow has moved from your code into the model, and that single move is the whole trade — flexibility in exchange for predictability, testability and a much larger surface for things to go wrong.

Everything else people call “agentic” — tools, memory, planning — are patches over specific limitations of a model call: it is stateless, it cannot act, it cannot verify. Ask of any proposed component: which gap does it close? If the answer is none, it is decoration.

QWhen should I not build an agent?▼
Quick answerWhenever the steps are the same every time. A workflow is cheaper, testable and predictable, and “when to build neither” is the question that saves the most money.

The rubric from Lab 1.5 asks four questions in a fixed order and stops at the first that decides — the order is the design, because asking about elegance before need is how teams talk themselves into a supervisor:

  1. Are the steps the same every time? → a workflow, no agent.
  2. Can one agent hold all the tools? → one agent. This is the default and a dozen tools is roughly the ceiling.
  3. Do the parts need separate authority — different credentials, independent audit, independent deployment? → supervisor and workers.
  4. Otherwise → peers that negotiate. Rare, and expensive.

Then the measurement gets a veto. A rubric that evidence cannot overrule is a preference with a flowchart.

QIs create_agent the same as create_react_agent? My snippet raises TypeError.▼
Quick answerLangChain 1.x replaced create_react_agent with create_agent, and the keyword is system_prompt=, not prompt=. The older names are all over the internet.
# what raises TypeError on langchain 1.4 agent = create_agent(model=llm, tools=TOOLS, prompt=SYSTEM) # what works agent = create_agent(model=llm, tools=TOOLS, system_prompt=SYSTEM)

prompt= was the 1.0-preview spelling. It is not deprecated — it is gone, and you get TypeError: create_agent() got an unexpected keyword argument 'prompt'. Same story for create_react_agent and the Langfuse v2 callback API: removed, not deprecated.

QIf create_agent does all of it, why did Lab 1.1 make me write the loop by hand?▼
Quick answerSo that you know what you are handing over. You write it once; in production you call create_agent.

The loop you wrote is the loop it runs: ask the model, execute whatever it asked for, feed the results back as ToolMessage, stop when it answers without a tool call. What create_agent adds is the part that is tedious and easy to get wrong — the step budget, the dispatch, pairing results to requests by tool_call_id, and a tool that raises not aborting the run.

It also earns you two things you will need this afternoon: you can read a tool_calls trace when something misbehaves, and you understand why bind_tools makes the loop safe — the tool name is checked against the tools you passed and the arguments against their schema, before your code sees them.

QDoes splitting into several agents really cost 3–10× the tokens?▼
Quick answerNot reliably, and on this workload not at all. Measured in Lab 1.4: tokens came out level (9,794 against 9,720). What doubled was model calls, latency rose by half, and the pass rate fell.

The reason is worth understanding rather than memorising: specialists get shorter prompts, so the per-call saving offsets the extra calls. Which axis the coordination tax lands on depends on how you split, and the only way to know is to measure your own.

AxisSingle agentSupervisor + 3 workers
Tokens9,7949,720 — level
Model calls1428 — 2×
Wall time14.1s21.3s
Pass rate5/50–3/5 across runs

So the argument against splitting is rarely the bill. It is the calls, the latency, and above all the accuracy.

QOur supervisor arm scored worse than the single agent. Did we build it wrong?▼
Quick answerAlmost certainly not — that is the expected result on a task this size, and it is the point of the lab.

Lab 1.4 audits the obvious suspect and clears it: the reason code survives the handoff intact, 5/5, both with a typed contract and with a substring search. So the data is not being mangled.

What is lost is context, not data. The single agent holds the ledger record, the policy text and the approval flag in one context when it composes its answer. The supervisor holds three separate summaries, each written by a worker that could not see the question. Every fact is present somewhere in the system; no single agent ever holds them all at once.

That is also why typing one handoff does not rescue the score. Typing an edge makes it assertable, which is how you ruled it out — it does nothing about the fragmentation, because the fragmentation is the architecture. Module 5's shared typed state is the real fix.

QWhy did rewriting the tool descriptions make such a difference?▼
Quick answerBecause the description is the only thing the model reads when choosing. Measured in Lab 1.3: same model, same five functions, same five questions — 2/5 to 5/5 on first-tool accuracy, from the descriptions alone.

Three parts of a @tool function are read by the model and by nothing else: the name (from the function), the description (from the docstring) and the argument schema (from the type hints). Everything else is for you.

The half people skip is saying what the tool is not for. “Returns the ledger record for one reference. Not for searching.” disambiguates against every other lookup tool you will ever add. A description that only says what a tool does gets it called when it should not be.

Practical order of operations: before you change the model, rewrite the descriptions. It is the cheapest accuracy in the course.

QI used response_format and result["structured_response"] came back None.▼
Quick answerThat happens, intermittently, and nothing is raised. The model answered in prose instead of calling the schema tool, so there is no object to give you.

response_format=Verdict asks the agent to finish by calling a tool that fills Verdict. A model that decides to reply in a sentence instead leaves the field empty. Your caller must handle it — treat a missing object as a failure to answer, not as an error-free run.

The wider lesson, which Module 8 pushes on: a contract fixes the shape, not the truth. Even when you get a well-formed Verdict, the values in it can be wrong. In Lab 1.3 the ordered procedure in the system prompt is what makes needs_human come out right — remove it and watch.

QHow many tools can one agent hold before I have to split it?▼
Quick answerRoughly a dozen is the working ceiling, and the real limit is not the count — it is whether the descriptions still disambiguate.

Adding a tool whose description overlaps an existing one costs you more than adding a tool in a new area. Before splitting, try the cheaper fixes: sharpen the two descriptions that collide, or merge two near-duplicate tools into one with an argument.

And split for the reason the rubric names, not for tidiness. Different credentials, independent auditability, or one worker that has to be deployable on its own are real reasons. “It felt cleaner” is what the coordination tax is charged for.

Day 1 · Module 2

Agentic Planning & Reasoning

9 questions
QWhat is LCEL, and why is everything joined with a |?▼
Quick answerIt composes a prompt, a model and a parser into one runnable with a shared interface: .invoke() for one, .batch() for many, .stream() to watch.
chain = prompt | model | StrOutputParser() chain.invoke({"payment": rec}) # one case chain.batch([...]) # the whole eval set, concurrently

Each stage has a clear job: the template turns variables into messages, the model returns an AIMessage, the parser pulls out a plain string. Swap the parser and you change what the chain returns without touching anything else.

.batch() is the one to remember. It sends the cases concurrently, which is the difference between an eval set people re-run on every change and one that was run once and quoted for a year.

QChain-of-Thought made it slower. Is it worth it?▼
Quick answerSometimes, and the honest answer is measure it on your task — which takes about five minutes with .batch() and an eval set.

CoT tends to earn its keep exactly where an answer needs two facts joined — the reason code and what policy says about it — and to do nothing at all where one lookup was enough. In the Lab 2.5 bake-off it scored highest and still did not win, because a cheaper arm cleared the acceptance bar.

One trap: if you score the whole reply rather than the final answer, CoT will look better simply by mentioning more words. That is why the labs mark the answer with ACTION: and score only what follows it.

QIf bind_tools exists, why did we hand-write a ReAct text parser at all?▼
Quick answerSo you can recognise the failure mode, and because you will meet models with no tool-calling API. In production you should not write one.

The classic ReAct formulation asks the model to emit Thought / Action / Action Input as text, which means you must parse it. Every parser is a contract the model never signed. Lab 2.2 collects eight ways a fluent writer legitimately drifts out of the format — markdown fences, bold headings, numbered steps, answering in clean JSON.

Then it shows the version with no parser in it: bind_tools sends the tool schema, and what comes back is already structured — name, args, id — validated before your code sees it. Keep the parser in your notes for the day you meet a model without that API, and know what you would be taking on: not eight formatting cases, but every argument your tools accept, forever.

QMy parser succeeded on every reply and the agent still got the answer wrong. How?▼
Quick answerThe format held and the argument drifted. Measured in Lab 2.2: under a prompt that had aged towards “be thorough”, 4/4 replies parsed and 0/4 were usable.
# strict instruction Action Input: PMT-1003 4/4 parsed · 4/4 usable # after six months of well-meaning prompt edits Action Input: {"payment_id": "PMT-1003"} 4/4 parsed · 0/4 usable

The regex is delighted. The tool name is right. The argument is a JSON object with a key your tool has never heard of, so the lookup returns nothing, the agent concludes the payment does not exist, and nothing anywhere reports an error.

This is worse than a parse failure, because a parse failure is loud. Your parser cannot catch it either — validating arguments was never its job. bind_tools rejects it at the boundary against the tool's schema.

QDoes JsonOutputParser(pydantic_object=Verdict) validate against that model?▼
Quick answerNo. It uses the schema only to write the format instructions in your prompt. What you get back is a dict, unchecked.

This surprises almost everyone, because you passed it a Pydantic model. Measured directly:

JsonOutputParser {"reason_code":"SR", "needs_human":"maybe"} -> dict, accepted PydanticOutputParser same input -> OutputParserException

Two required fields missing and a string where a boolean belongs, and it sailed through. If you want the schema enforced, use PydanticOutputParser (which raises) or with_structured_output (which also constrains the generation).

QWhich output parser should I actually use?▼
Quick answerwith_structured_output when the model supports it; a chain with PydanticOutputParser when it does not.
ParserYou get backValidated?

Both forms work for the Lab 2.3 plan — each returned a validated Plan 3/3 on this model. Prefer the structured-output route because the stack shapes the generation as well as checking the result. If you take the parser route, pair it with OutputFixingParser (now in langchain_classic.output_parsers) so a drifted reply gets one repair attempt rather than an exception.

QRetry or re-plan — how do I tell which one a failure deserves?▼
Quick answerAsk whether the world misbehaved or the plan was wrong. Retry the world. Re-plan the plan. Never retry a plan.

A timeout, a 503, a rate limit: transient. Retry, with a bound. “No such tool”, “no payment found”, an invalid argument: the plan was wrong, and retrying it is a loop that burns budget and finishes nowhere. The reference bug looks like this, and it is everywhere:

except Exception: retry() # what kind of exception? nobody asked

Lab 2.3 also validates the plan before running it, which matters because the model regularly invents a step naming a tool that does not exist. That is not the model misbehaving; it is what planners do. Catching it before execution is the whole value of a typed plan.

QHow many reflection rounds should I run?▼
Quick answerUntil the critic stops finding anything — and give it a way to say so. Typically a large gain on round one, a small one on round two, noise after that.

The failure mode is built into the request: a critic asked to find faults will find faults, because that is what you asked for. If it has no way to pass, it will invent something and you will loop forever, getting worse.

So the instruction must include the exit: “If there is nothing material to fix, reply with exactly: NO ISSUES”. Then stop on that. Try it on an answer that is already correct and count the rounds before it starts inventing — that number is your real ceiling.

QWhich reasoning architecture should I default to?▼
Quick answerThe cheapest one that clears a bar you wrote down before you ran anything. Very often that is a direct answer.

Write three clauses first: a minimum pass rate, any case that is disqualifying however good the average, and how long a caller will wait. Then run all four arms over one eval set.

In Lab 2.5 that rule rejects ReAct at 80% while accepting Reflection at the same 80% — because ReAct got the sanctions case wrong and the bar named that case as disqualifying. A pass rate is an average; averaging is exactly what hides the case you cannot afford to lose.

Once an arm clears the bar, extra quality is something you are paying for and not using. So the cheapest that clears wins, and only a tie on cost is settled by pass rate.

Day 1 · Module 3

Memory, State & the LangGraph Substrate

10 questions
QWhen do I need LangGraph instead of create_agent?▼
Quick answerWhen you need to see, steer or resume the state. Not before.

create_agent is enough for one loop over one set of tools where a crash mid-run is acceptable. Reach for a graph when state must be explicit and inspectable, the run must survive a restart, there are branches or cycles or parallel paths, or a human must approve a step mid-run.

Note the honest framing: you are not dropping to LangGraph for the graph. You are doing it for the state the graph forces you to declare — and a declared state is one you can assert on, resume, and show an auditor.

Qtrim_messages raised NotImplementedError. What did I do wrong?▼
Quick answerNothing. You passed token_counter=llm, and langchain-openai can only count for models tiktoken has an encoding for. A gateway-served model is not one.
# raises on any self-hosted or gateway-served model trim_messages(msgs, max_tokens=200, token_counter=llm) # works: a plain function over the message text trim_messages(msgs, max_tokens=200, token_counter=count_tokens_approximately)

This is not a quirk of our sandbox — it is what happens to every model that is not on tiktoken's list, and it tends to show up under load rather than in development. Lab 3.1 teaches it deliberately.

While you are there: use strategy="last" and include_system=True. Trimming that drops the standing instruction is the worst possible trim.

QWhat is a reducer, and when do I actually need one?▼
Quick answerA reducer says how two writes to the same state key merge. The default is replace. You need one on any key more than one node writes.
findings: list # default: replace findings: Annotated[list, add] # declared: append

With the default, node B's write silently discards node A's. No error, no warning. Combine default-replace with parallel branches — three workers writing one key — and you have silent data loss that looks like the agents simply did not find anything.

The rule is short enough to remember: any key more than one node writes needs a declared reducer. Keys only one node owns are fine on the default.

QTwo of my nodes wrote to the same key and the earlier findings vanished.▼
Quick answerThat is the default reducer doing exactly what it says. See the question above — declare one.

It is worth reproducing once on purpose, because the symptom is so unhelpful: the run completes, the state is well-formed, and the answer is composed from a third of the evidence. Nothing distinguishes it from a run where the tools genuinely found nothing.

Lab 3.3's self-check runs a real two-node graph and asserts both findings survive, which is the cheapest possible regression test for this and takes no model at all.

QWhat does a checkpointer actually buy me?▼
Quick answerIt writes the full state after every node, under a thread_id. Four capabilities fall out of that one fact.
You getBecause
Resumethe pod restarts at step 3 of 4 and continues rather than starting over
Human in the loopinterrupt_before stops the graph, you decide, then resume
Time travelinvoke from an older checkpoint's config and take a different path
Audit trailget_state_history() — what was known, and when

Be precise about the approval one, though. A checkpointer is what lets you pause and resume a run. It is not the only way to build a gate — a service that returns a recommendation with a requires_approval flag and has no write tool at all is a perfectly good gate, and that is what the capstone does. It simply cannot resume mid-run.

QI rewound to an earlier checkpoint and the graph paused again instead of finishing. Bug?▼
Quick answerNo — and this surprises everyone. interrupt_before is a property of the compiled graph, not of a particular run, so every path through it pauses.
app.invoke(None, older_checkpoint_config) app.get_state(cfg).next -> ('write_note',) # paused at the gate again answer -> None

The replay runs forward from where you sent it and stops at the gate exactly as the first run did. If you want it to finish, resume it again. Two other things worth knowing while you are here: resuming passes None as the input — that means carry on, not start again — and a config carrying only a thread_id points at now, so a rewind needs the older checkpoint's own config.

QIs thread_id just a session id?▼
Quick answerClose enough — and getting it wrong is the commonest way agent memory leaks between users.

Each thread_id is a separate conversation with its own history. Key it by the thing that should be isolated: a case, a ticket, a user session. In Lab 3.1 two threads hold two different client contacts and neither leaks into the other — with no code of yours managing either.

Now picture the same code with a constant thread_id. Every case appends to one history, and the second client's question gets answered with the first client's details. It is a one-line bug with a regulatory-incident shape.

QShared state or private state for a multi-agent system?▼
Quick answerMixed, in practice: shared facts, private drafts. Shared is cheap and consistent; private contains a mistake but re-sends context and duplicates work.

Shared state is what stops the context fragmentation Lab 1.4 measured — agents that cannot see each other's work produce worse answers than one agent that can. So the answer to poisoning is not to retreat into isolation.

The discipline is about what earns a place in the shared record. An agent's uncertain working notes belong in its own scratch area, where they can be inspected and not believed. The shared findings list is what every other agent treats as fact, so the bar for entering it should be higher than “an agent said so”.

QThree agents independently agreed. Isn't that corroboration?▼
Quick answerNo — it is an echo. If the first agent was wrong, every later agent was correct given what it was told, and the critic was checking consistency rather than truth.

This is what makes context poisoning different from an ordinary bug. Nothing errors. No exception, no anomaly in the trace, no disagreement to investigate. There is just a confident answer built on one bad input, and three concurring agents reading as evidence.

A consistency check cannot catch a bad premise. If you want a critic that can, it has to be able to go back to the source — or to refuse.

QWe added provenance to every finding and it still got poisoned. What actually stops it?▼
Quick answerPermission to refuse. Measured in Lab 3.5 on identical poisoned evidence: 3/3 flagged the inconsistency with a refusal clause in the prompt, 0/3 without it.

Provenance is not verification — every finding in the poisoned run passes the trustworthiness check, because the wrong one is correctly attributed to a real source. What provenance buys you is the ability to trace and quarantine once you know a source was wrong: drop that source, re-decide on what survives. That is recovery, and it is worth having.

Prevention is one sentence in the system prompt:

… if the evidence is inconsistent or insufficient, say so instead of deciding.

With it, the reviewer notices that a settled payment needs no next action and says the evidence is inconsistent. Without it, it does what it was asked — decides — and closes the case. The model could catch the poisoning all along; what it lacked was permission. An agent told only to decide will decide, on whatever it has, every time.
